# Networking
Listen server first; authoritative logic does not depend on a local player or UI, preserving a future dedicated-server path. Movement uses Unreal CharacterMovement. No custom client position or speed RPCs.

Clients send begin/end intent through their owned replicated interaction component. Server derives pawn, view origin, control rotation and trace target; client cannot send a target, duration or result. Visibility trace limits range and rejects occlusion. The server checks eligibility at start, during the hold and at completion. Remote control rotation is still client aim intent, never permission to modify arbitrary gameplay state.

Each pawn owns one pending timer/target. Release cancels, invalid aim/permission cancels, teardown clears timers. Starts are throttled. The test actor serializes mutations on the authoritative game thread, increments once per completed hold and replicates only the changed count to all relevant clients. RepNotify updates presentation and is called explicitly on the listen host. Completion implementations must independently validate mutable actor state.

Gate 1's executed two-player and latency checks are recorded in GATE_1_VALIDATION.md; Gate 1 is accepted.

Gate 2 seat occupancy is assigned only on the server, rechecked at hold completion, and replicated as a survivor reference on each seat component. The owner-only controller SeatedVehicle reference supports exit/input routing. Driver entry changes possession to the RV; passenger entry preserves survivor possession. Seat assignment, survivor attachment and disabled movement replicate to observers. Exit releases occupancy only after authority finds a grounded, clear capsule position outside RV geometry. Moving exits, tall obstacle tops and excessive drops are rejected.

Driving sends only throttle/brake-reverse axis, steering axis and handbrake intent through the owned controller at 20 Hz (unreliable). The server requires that controller to possess this vehicle and own its occupied driver seat, rejects nonfinite values, clamps axes, and applies a 0.5-second stale-input timeout with handbrake. Chaos integrates forces on the server. Native physics replication, including autonomous-proxy physics updates, carries the resulting RV movement; no client transform RPC exists. Chaos network physics prediction is disabled for this initial server simulation configuration. The inherited Chaos input RPC ignores client arguments and copies only the server's already processed state. Client vehicle-manager PreTickGT/Update paths are disabled, since disabling component tick alone does not disable Chaos manager updates. Proxy gravity is also disabled: without local suspension, it made sleeping parked clients sink below the server and misalign entry traces. Server rigid-body replication supplies vertical motion.

On disconnect, ARVPlayerController releases its seat and unpossesses the RV before Unreal's PawnLeavingGame destruction path. The preserved survivor is destroyed, driving input is cleared, and the shared RV remains available. Validation results and exact Chaos settings belong in GATE_2_VALIDATION.md. Remote physics has correction/smoothing limits; Gate 2 does not promise vehicle prediction or moving-interior stability.

## Gate 3 reference frame (accepted)

Standing passengers remain ordinary survivor pawns with native CharacterMovement prediction and based-movement replication. Movable, simple collision floors carry the `RVPassengerPlatform` tag. URVPassengerReferenceFrameComponent derives membership independently from each role's authoritative/replicated native movement base; its observed frame pointer is not a separate client-authoritative state channel. No passenger transform RPC, tick teleport or walking attachment is added. Native UE 5.8 base-relative acceleration/location paths are retained.

Inside the frame, native deferred physics-base carry ignores the base actor during its carry sweep; ordinary walking sweeps still collide with cabin walls/furniture. Physics pushing is disabled for the standing character. Interior capsule radius and walking speed are configurable per-character defaults (30 cm and 200 cm/s), and original outside settings are restored on leaving/teardown. This policy is provisional for the measured Class C aisle, not a later fatigue/resource system.

Workstation traces still run from the survivor's eye/control rotation. Clients send only accepted begin/end interaction intent; authority retraces range, line of sight and permission throughout the hold. The attached station's local transform and completion count replicate through native attachment/property replication. Moving and turning interaction correctness must be demonstrated in live tests, including separate processes; compilation/base membership alone is insufficient.

Development diagnostics use `rv.Passenger.Debug` (1: frame/corrections, 2: floor/base changes), local displacement, native base identity and acknowledged-move correction distances. Correction metrics use saved relative positions only when the acknowledged move and new correction share the same base. Initial fixture teleports are excluded from steady-state measurements. Test scripts and measured results belong in GATE_3_VALIDATION.md; this section does not itself declare acceptance.

Gate 3 additionally prevents client vehicle physics-state creation and destroys any pre-role vehicle simulation during BeginPlay. Chaos async submission continues independently of game-thread tick guards, so those guards alone are insufficient. The mesh rigid body remains available for native server physics replication; client vehicle simulation/forces are absent. Native wheel-body/joint cleanup remains, and proxy gravity is disabled. This is a targeted shared vehicle networking fix and passed the original Gate 2 regression (90 live + 20 paired checks).


Final Gate 3 tests passed both walking/driver roles in shared and separate processes, including server outgoing 100 ms/2% loss. Native prediction/corrections remain enabled; the emulated client walker recorded four small strong-turn corrections, maximum 1.85 cm. See GATE_3_VALIDATION.md and permanent paired/telemetry records for measured drift and observer timing limits. No guarantee for larger sessions, airborne passengers or arbitrary network faults is added.

## Gate 4 inventory/storage (in development)

Owned inventory intent RPCs accept item GUID, quantity and transfer direction. Authority derives the source inventory and selected container and revalidates quantity, capacity, range and line of sight. Serial source-to-destination transactions preserve quantity and instance condition; full-record moves preserve identity, splits receive a new identity. FastArray contents replicate deltas; selected-container/feedback properties are owner-only. Clients do not submit item definitions or fabricated instance data.

All server mutation implementations explicitly reject non-authority execution. Local intent dispatch uses a weak next-tick delegate before invoking the network RPC, because the editor Python script guard otherwise forces actor RPC callspace to local execution. No weak delegate retains a pawn/world. Native object attachment handles dropped items on a moving passenger floor; this adds no passenger transform or movement RPC.

Gate 4 multiplayer acceptance, separate-process results and network-emulation measurements are tracked in GATE_4_VALIDATION.md. The accepted Gate 1–3 architecture is preserved.
